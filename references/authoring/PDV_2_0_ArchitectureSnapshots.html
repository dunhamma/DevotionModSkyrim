Devotion Architecture Shift

Two snapshots of the same mod. 1.5 ships one script that holds every system. 2.0 splits that script into nine owners the host binds at startup, with the ten race systems behind a single interface. Each figure stands alone as a reference.

1.5 read from the shipped Devotion tree · 2.0 read from Devotion-V3Dev at branch tip
counts are direct readbacks and one module-census gate, taken after deployment

Before — Devotion 1.5

shipped

Every runtime system lives in one file. The four entry points all call into it, and the deity, prince and substrate records around it carry data only. There is no seam between a race behaviour and the panel that displays it — changing one means opening the file that holds both.

After — Devotion 2.0

rebuilt

The same four entry points now reach a host that does three things: start the systems, hold a typed reference to each, and run the one shared tick. Behaviour sits in nine owners beside it. The ten race systems share one interface, and the host binds exactly one race adapter per character at startup — so a race change is a rebind, not a branch.
